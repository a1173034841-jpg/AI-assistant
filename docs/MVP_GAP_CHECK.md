# MVP 差距检查

## 1. 当前已经具备

### 产品主路径

- 已有问卷字段说明页。
- 已有售后反馈报告工作台。
- 已支持模拟问卷批次切换。
- 已支持项目周期和日期筛选。
- 已支持区域、城市、服务中心层级下钻。
- 已支持原始评论查看。

### 报告能力

- 已有总报告和专项报告。
- 已有服务问题闭环、满意度归因、区域 / 城市下钻、活动体验复盘、口碑素材与风险。
- 已有重点关注板块：好区域典型清单和风险区域典型清单，均可展示多张卡片。
- 已有证据原话展开。
- 已有复制报告按钮。

### 指标能力

- 已覆盖反馈量、平均服务评分、推荐意愿评分、推荐者 / 贬损者、被动者、满意率、低分反馈、负向占比、待跟进、联系授权率、需人工复核、风险服务中心和高发服务环节。
- 指标卡已能解释分数来源。
- 原话证据已能追溯服务评分、推荐意愿评分、来源问卷、服务中心和服务场景。

### 技术基础

- Vite + React + TypeScript 已完成。
- 本地 mock 数据和规则分析层已完成。
- 单元测试覆盖核心分析流。
- `npm test` 和 `npm run build` 已通过。

## 2. 距离可演示 MVP 还差

### 必须补齐

1. **真实 Excel / CSV 解析**

当前还是模拟批次。要进入 MVP，至少需要支持选择本地文件、读取表头、解析记录。

2. **字段映射预览**

需要让运营确认：哪一列是提交时间、项目名、城市、服务中心、服务评分、推荐意愿评分、开放反馈、服务场景、授权联系。

3. **导入结果确认页或弹窗**

系统识别出的项目名和时间范围必须可确认、可修改。

4. **大样本评论列表**

真实业务可能几千到上万条，原始评论区需要分页、搜索或虚拟滚动，不能一次性渲染全部。

5. **报告导出**

复制按钮已有，但 MVP 最好支持导出 Markdown / Word / 文本，方便进入周报和复盘材料。

6. **更真实的分析层**

当前是规则归因。MVP 可以先保留规则，但需要接一个 LLM 占位接口或 prompt 层，证明后续可以生成更自然的复盘文案。

## 3. 可以暂缓

- 登录和权限。
- 历史报告库。
- 第三方问卷 API 对接。
- 数据库。
- 可视化 Dashboard。
- 企业微信或 CRM 回写。
- 多人协作和审批流。

## 4. 最大产品风险

### 风险一：导入体验不成立

如果不能顺利导入 Excel / CSV，这个工具就只能演示，不能验证真实工作流。

### 风险二：报告像模板

如果报告不能从原始评论中抽出具体共性、典型证据和动作建议，就会回到“帮我总结一下”的弱价值。

### 风险三：大样本不可用

售后反馈真实样本量可能很大，必须支持筛选、分页和按时间排列。

### 风险四：指标解释不被信任

运营团队会问“这个分数怎么算的”。所以每个指标都要能说明字段来源、计算口径和样本范围。

## 5. 下一步建议

### 先做真实 MVP 的最小补齐

1. 做 Excel / CSV 上传和解析。
2. 做字段映射确认。
3. 做导入确认：项目名、时间范围、记录数、异常行。
4. 做原始评论分页。
5. 做报告导出。

### 再做 AI 质量提升

1. 把当前规则输出作为结构化输入。
2. 增加 LLM 生成报告层。
3. 约束输出必须引用 evidenceQuotes。
4. 增加“需人工复核”的提示。

## 6. 当前判断

当前版本已经接近“可讲清楚产品价值的演示原型”，但还不是可真实使用的 MVP。

真正 MVP 的门槛是：运营能上传一份真实问卷导出表，确认字段后，在指定项目和日期范围内得到可复制报告，并能下钻查看原始评论和分数来源。
