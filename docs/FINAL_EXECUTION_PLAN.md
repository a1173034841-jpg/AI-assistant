# 主机厂售后反馈连续复盘与分析工作台最终执行方案

> 确认稿。本文档用于统一产品方向、用户场景、功能边界、技术路线和实施里程碑。确认后，后续 PRD、数据规格、前端原型和开发任务都以本文档为主线。

## 1. 项目定位

本项目不是单纯的问卷工具，也不是只帮运营写一段总结的文案工具，而是面向主机厂售后运营团队的 **反馈数据分析与复盘报告生成工作台**。

它承接问卷星、腾讯问卷、App 内问卷、短信链接、企微链接等渠道收集到的售后服务反馈，将评分、时间、项目、区域、服务中心和用户原话统一标准化，自动生成一份可追溯、可下钻、可复制、可继续追问的售后复盘报告。

用一句话解释：

> 问卷负责把车主声音收进来；本工作台负责把车主声音变成运营能判断问题、追踪趋势、推动闭环和交付报告的材料。

## 2. 第一目标用户

MVP 第一目标用户是离用户最近的主机厂运营岗位：

| 用户角色 | 典型任务 | 需要的结果 |
| --- | --- | --- |
| 区域运营 | 看某个周期内区域、城市、服务中心的售后体验表现 | 找到好区域、差区域、问题共性和下周跟进重点 |
| 服务运营 | 看负反馈、低分反馈、待回访反馈和服务环节问题 | 形成服务问题闭环清单、责任动作和回访口径 |
| 用户运营 | 看活动、社群、触达后的用户反馈 | 总结活动效果、用户关注点、正向素材和下次优化方向 |

品牌口碑、内容团队可以作为后续扩展用户，但不作为 MVP 架构的第一驱动。

## 3. 当前项目现状

### 3.1 已有基础

当前项目已经完成一个 React + Vite + TypeScript 的前端原型，具备以下能力：

- 分析工作台页面。
- 标准 CSV 测试数据和本地 CSV 上传解析。
- 规则分析函数。
- 项目、时间、区域、城市、服务中心筛选。
- 指标计算：反馈量、平均服务评分、净推荐值、推荐者、贬损者、满意率、低分反馈、负向占比、待跟进、联系授权率、人工复核、覆盖区域等。
- 重点关注：好区域典型、风险区域典型。
- 总报告、专项报告、证据原话、原始评论下钻。
- 单元测试覆盖部分分析规则和导入校验。

### 3.2 当前主要问题

当前原型能够说明方向，但还不是可真实使用的 MVP，主要问题是：

1. **工作台逻辑仍然偏“手动选择项目再分析”**
   - 目标形态应是上传问卷表格后自动生成完整复盘。
   - 时间层级应优先于项目层级。

2. **时间延续性不足**
   - 当前更多是单项目、单时间段分析。
   - 目标需要支持日、周、月、季度、年和自定义时间段，并能跨项目、跨周期对比。

3. **数据库与检索底座尚未建立**
   - 当前已经接入前端 CSV 解析和规则函数，但尚未建立持久化数据库与检索层。
   - 真实 MVP 需要 SQL、BM25 和 Chunk/Vector 的混合检索分析架构。

4. **Agent 追问层尚未实现**
   - 目标不是只给静态报告，而是让运营能围绕当前数据继续问：
     - 为什么这个城市评分下降？
     - 哪些服务中心低分集中？
     - 某个项目和上个月相比问题是否变化？
     - 能否列出可回访的低分样本？

5. **文档主线需要统一**
   - 现有部分文档仍保留“项目优先、步骤式手动工作流、专项输出优先”的旧口径。
   - 后续需要统一为“上传自动复盘、时间优先、项目集合分析、Agent 追问”的新架构。

## 4. 核心用户痛点

### 4.1 反馈收集不是最大问题，反馈加工才是最大问题

运营团队通常已经有问卷星、腾讯问卷、App 问卷、短信和企微链接。真正低效的环节不是“有没有问卷”，而是导出结果后如何处理几百、几千甚至上万条反馈。

### 4.2 运营需要的是结论，不是原始表格

原始表格里有评分、城市、服务中心、开放题原话，但运营真正要回答的是：

- 本期服务体验整体表现如何？
- 哪些区域和服务中心表现好，可以复制？
- 哪些区域和服务中心风险高，需要处理？
- 体验变化的主因是什么？
- 哪些用户反馈可以直接进入回访或闭环？
- 哪些原话可以支撑报告结论？

### 4.3 单一净推荐值不足以支撑售后运营决策

净推荐值可以为负，也可以反映推荐意愿结构，但它不能单独回答全部售后问题。MVP 必须建立完整的指标体系，包括体验结果、问题风险、闭环处理、范围覆盖和数据质量。

### 4.4 静态报告不够，运营还要继续追问

一份自动生成的复盘报告只能覆盖默认问题。真实运营会继续追问细项，比如某个城市、某个服务中心、某个服务环节、某段时间、某个项目集合的变化。因此产品必须具备 Agent 追问能力。

### 4.5 时间和项目必须能连续分析

售后运营不是一次性分析。一个月可能有四周，每周有不同项目；也可能需要看一个季度内所有项目的共同问题。产品必须支持：

- 单日、单周、单月、季度、年度分析。
- 自定义时间段分析。
- 一个时间段内单项目、多项目或全部项目分析。
- 跨时间段对比。
- 跨项目集合对比。

## 5. 目标产品形态

目标产品形态是 **上传即生成复盘，报告可下钻，问题可追问**。

核心链路如下：

```txt
上传问卷 Excel / CSV
-> 字段识别与映射确认
-> 导入校验与标准化入库
-> 按时间范围自动生成 8 模块完整复盘
-> 支持项目集合、区域、城市、服务中心下钻
-> 支持查看指标口径、分数来源和原始评论
-> 支持 Agent 围绕当前数据继续追问
-> 支持复制 / 导出报告和闭环清单
```

## 6. 产品使用逻辑

### 6.1 默认操作路径

运营第一次使用时，不应该先面对一堆复杂筛选器，而应按以下路径完成：

1. **上传数据**
   - 上传来自问卷星、腾讯问卷、App 内问卷或其他平台的 Excel / CSV。

2. **确认字段与导入校验**
   - 系统识别提交时间、项目名称、来源、区域、城市、服务中心、服务评分、推荐意愿评分、开放反馈、授权联系等字段。
   - 运营只处理识别失败或需确认的字段。

3. **自动生成默认复盘**
   - 系统根据数据中的时间范围，自动生成完整报告。
   - 默认视图优先展示当前数据覆盖周期的整体复盘。

4. **切换时间粒度**
   - 日、周、月、季度、年、自定义时间段。
   - 时间是第一层级，项目是时间范围内的分析对象。

5. **选择项目集合**
   - 当前时间范围内全部项目。
   - 单个项目。
   - 多个项目。
   - 按项目类型分组。

6. **下钻范围**
   - 全国。
   - 区域。
   - 省份 / 城市。
   - 服务中心。
   - 原始评论。

7. **使用 Agent 追问**
   - 围绕当前报告、指标、原话、时间段、项目集合和地区范围提问。
   - 无关问题拒绝回答。

8. **导出交付物**
   - 总复盘报告。
   - 服务问题闭环清单。
   - 区域 / 服务中心诊断。
   - 用户运营复盘。
   - 口碑素材与风险摘要。

### 6.2 回退逻辑

工作台每一步必须能回退，且回退后不丢失上下文：

| 当前动作 | 可回退到 | 回退后行为 |
| --- | --- | --- |
| 报告生成后发现时间范围不对 | 时间选择 | 重新计算指标、报告和证据 |
| 报告生成后发现项目范围不对 | 项目集合 | 保留时间范围，重新合并所选项目 |
| 下钻到服务中心后想看城市 | 城市层级 | 回到城市汇总，服务中心选择清空 |
| Agent 追问后想看证据 | 证据原话 | 展开回答引用的原始反馈 |
| 字段映射有误 | 字段映射确认 | 重新标准化数据并刷新报告 |

## 7. 默认自动复盘 8 个模块

上传数据并完成校验后，系统默认生成以下 8 个模块：

| 模块 | 回答的问题 | 主要数据来源 |
| --- | --- | --- |
| 数据概览 | 本次数据覆盖多少反馈、时间、项目、区域和服务中心？ | SQL 结构化统计 |
| 整体体验表现 | 本期服务体验整体好不好？相比其他周期是否变化？ | 服务评分、净推荐值、满意率、趋势 |
| 核心问题判断 | 最主要的问题是什么，集中在哪些服务环节？ | 低分、负向文本、主题归因 |
| 时间 / 项目维度复盘 | 哪些时间段、哪些项目表现异常或值得复盘？ | 时间粒度、项目集合、趋势对比 |
| 区域 / 城市 / 服务中心表现 | 哪些区域做得好，哪些区域需要处理？ | 地区聚合、服务中心聚合 |
| 用户原话证据 | 哪些原话支撑报告结论？ | BM25、标签、证据选择 |
| 运营动作建议 | 接下来应该先处理什么，谁来跟进，怎么闭环？ | 风险级别、授权联系、问题类型 |
| 可继续追问的问题 | 运营还可以继续问哪些关键问题？ | 当前报告上下文、数据缺口 |

## 8. 指标体系

MVP 指标体系分为五类，避免只围绕净推荐值展开。

### 8.1 体验结果指标

| 指标 | 说明 |
| --- | --- |
| 平均服务评分 | 当前筛选范围内服务评分均值 |
| 净推荐值 | 推荐者占比减去贬损者占比，范围为 -100 到 100，可以为负 |
| 推荐者 | 推荐意愿评分 9-10 的样本数 |
| 被动者 | 推荐意愿评分 7-8 的样本数 |
| 贬损者 | 推荐意愿评分 0-6 的样本数 |
| 满意率 | 服务评分达到满意标准的样本占比 |

### 8.2 问题风险指标

| 指标 | 说明 |
| --- | --- |
| 低分反馈 | 服务评分低或推荐意愿评分低的样本 |
| 负向占比 | 负向文本或低分样本占全部样本比例 |
| 口碑风险 | 有扩散风险、强烈不满或明确投诉倾向的反馈 |
| 风险服务中心 | 负向反馈、低分反馈或待跟进样本集中的服务中心 |
| 高发服务环节 | 服务发起、接待、维修质量、补能、App/OTA、活动等问题高发环节 |

### 8.3 闭环处理指标

| 指标 | 说明 |
| --- | --- |
| 待跟进反馈 | 已授权联系、低分、高严重度或明确要求处理的样本 |
| 联系授权率 | 愿意被联系的反馈占比 |
| 未解决问题 | 用户明确表达问题未解决的反馈 |
| 需人工复核 | 字段缺失、语义不清、风险较高或模型无法确定的样本 |

### 8.4 范围覆盖指标

| 指标 | 说明 |
| --- | --- |
| 反馈量 | 当前范围内反馈总数 |
| 覆盖项目数 | 当前时间范围内纳入分析的项目数量 |
| 覆盖区域 / 城市 / 服务中心 | 当前数据覆盖的运营范围 |
| 来源渠道分布 | 问卷星、腾讯问卷、App 内问卷等来源比例 |

### 8.5 数据质量指标

| 指标 | 说明 |
| --- | --- |
| 必填字段完整率 | 提交时间、评分、城市、服务中心、原话等字段完整程度 |
| 指标可计算率 | 能计算服务评分、净推荐值、地区聚合和文本归因的记录占比 |
| 隐私风险 | 是否存在明文手机号、车牌、VIN、住址等敏感信息 |
| 样本有效性 | 当前样本量是否足以支撑报告结论 |

## 9. 核心功能清单

### 9.1 数据导入与字段映射

必须实现：

- Excel / CSV 上传。
- 表头识别。
- 字段映射确认。
- 标准模板下载。
- 多来源文件合并。
- 导入批次记录。
- 异常行提示。

不做：

- 不自研完整问卷创建器。
- 不接第三方问卷 API。
- 不做复杂问卷题型和跳题逻辑。

### 9.2 时间优先分析

必须实现：

- 日、周、月、季度、年、自定义时间段。
- 默认根据上传数据推断覆盖时间。
- 时间段内项目集合分析。
- 跨周期对比接口预留。

### 9.3 项目集合分析

必须实现：

- 时间范围内全部项目。
- 单项目分析。
- 多项目合并分析。
- 项目类型分组。
- 项目与来源渠道分离。

关键原则：

> 项目是运营分析对象；问卷星、腾讯问卷、App 内问卷只是数据来源。

### 9.4 区域与服务中心下钻

必须实现：

- 全国总览。
- 区域筛选。
- 城市多选。
- 服务中心单点下钻。
- 服务中心原始评论列表。
- 按提交时间排序。
- 大样本分页或虚拟列表。

### 9.5 自动报告生成

必须实现：

- 上传后默认生成完整复盘。
- 总报告不是专项报告合集，而是管理层能直接看的判断摘要。
- 每个结论必须引用指标或原话证据。
- 报告可复制、可导出。

### 9.6 专项输出

必须实现：

- 服务问题闭环清单。
- 满意度归因。
- 区域 / 城市 / 服务中心诊断。
- 活动体验复盘。
- 口碑素材与风险摘要。

专项输出的定位是总报告后的下钻交付物，不是总报告的重复版本。

### 9.7 原话证据与代表性判断

必须实现：

- 每个关键结论至少有原话证据。
- 证据必须能追溯到服务评分、推荐意愿评分、提交时间、服务中心、来源渠道和项目。
- 代表性原话不能只靠“看起来像”，需要有选择规则：
  - 主题出现频次高。
  - 能代表当前结论。
  - 与评分或负向 / 正向标签一致。
  - 不是孤立个案，或已明确标记为高风险个案。

### 9.8 Agent 追问

必须实现：

- 开放式聊天入口。
- 只回答本工具、本数据、本售后运营分析相关问题。
- 无关问题拒绝回答。
- 回答必须说明依据：指标、筛选范围、原话证据或数据不足。
- 支持 SQL、BM25、Chunk/Vector 检索结果作为上下文。

Agent 可回答的问题示例：

- 这个月最主要的负反馈是什么？
- 华南区域哪个城市问题最多？
- 五一项目和端午项目相比，服务中心问题有什么变化？
- 找出所有授权联系且低分的反馈。
- 帮我把这批风险服务中心整理成闭环清单。

Agent 应拒绝的问题示例：

- 写一首诗。
- 查询天气。
- 讨论与当前售后反馈无关的汽车维修建议。
- 生成没有数据依据的结论。

## 10. 技术路线图

### 10.1 当前技术栈

- 前端：Vite + React + TypeScript。
- 样式：普通 CSS。
- 图标：lucide-react。
- 测试：Vitest。
- 当前数据：标准 CSV 测试数据 + 本地 CSV 上传解析。
- 当前分析：规则函数。

### 10.2 目标架构

```txt
前端工作台
  -> 文件上传与字段映射
  -> 导入校验
  -> 后端服务
  -> Supabase 管理的 SQL 结构化数据库
  -> BM25 精准文本检索
  -> Chunk / Vector 语义检索
  -> 分析与报告生成服务
  -> Agent 追问服务
  -> 报告导出与历史留存
```

### 10.3 SQL 数据库

SQL 用于处理轻量、准确、结构化的事实：

- 导入批次。
- 项目。
- 问卷来源。
- 提交时间。
- 区域、城市、服务中心。
- 服务评分、推荐意愿评分。
- 服务场景。
- 授权联系。
- 指标聚合。
- 报告版本。

生产方向使用 Supabase 管理后端数据库。Supabase 底层基于 PostgreSQL，适合承接结构化表、权限、导入批次、报告记录和 Agent 对话记录；当前前端原型仍可用本地 CSV 完成验证，但数据接口按 Supabase 目标预留。

### 10.4 BM25 检索

BM25 用于精准字段和关键词检索：

- 等待时间长。
- 解释不清楚。
- App 预约失败。
- 补能排队。
- 服务顾问态度。
- 活动权益说明。

BM25 更适合找“用户明确说过某个词或近似词”的反馈。

### 10.5 Chunk / Vector 语义检索

Chunk + Vector 用于复杂语义场景：

- 同一个用户在不同时间段、不同问卷中的反馈变化。
- 多项目之间相似问题的归并。
- 用户没有说同一个词，但表达了同一类问题。
- 跨月、跨季度的问题主题演化。
- Agent 对复杂追问进行语义召回。

Chunk 如何切分后续单独设计。当前先确认架构方向：精准字段和关键词走 BM25，复杂语义走 Chunk / Vector。

### 10.6 Agent 编排

Agent 不直接“凭空回答”，而是先判断问题类型：

| 问题类型 | 检索 / 计算方式 |
| --- | --- |
| 指标统计 | SQL |
| 时间、项目、区域筛选 | SQL |
| 精准关键词查找 | BM25 |
| 相似表达、跨周期归因 | Chunk / Vector |
| 报告生成 | SQL + BM25 + Vector + 模板约束 |
| 无关问题 | 拒绝回答 |

## 11. 建议数据模型

### 11.1 核心表

| 表 | 用途 |
| --- | --- |
| import_batches | 记录每次上传、来源文件、导入状态 |
| survey_sources | 记录问卷星、腾讯问卷、App 内问卷等来源 |
| projects | 记录业务项目，不等同于问卷来源 |
| feedback_records | 标准化后的每条反馈 |
| service_centers | 服务中心主数据 |
| metric_snapshots | 按时间、项目、地区聚合后的指标快照 |
| report_runs | 每次报告生成记录 |
| report_sections | 报告 8 个模块内容 |
| evidence_quotes | 报告引用的原话证据 |
| agent_messages | Agent 追问历史 |

### 11.2 关键关系

```txt
import_batches 1 -> n feedback_records
projects 1 -> n feedback_records
survey_sources 1 -> n import_batches
service_centers 1 -> n feedback_records
report_runs 1 -> n report_sections
report_sections 1 -> n evidence_quotes
agent_messages n -> 1 report_runs
```

目标：把项目主线从旧的“项目优先手动工作流”统一为“上传自动复盘、时间优先、项目集合分析、Agent 追问”。

交付物：

- 更新 PRD。
- 更新 MVP_SCOPE。
- 更新 DEV_DESIGN。
- 更新 DATA_AND_ANALYSIS_SPEC。
- 更新 METRIC_SYSTEM。

验收标准：

- 只看 DEV_DESIGN 能画出新工作台。
- 只看 DATA_AND_ANALYSIS_SPEC 能开始建数据表、CSV 导入数据和压测样本。

### M1：真实导入 MVP

目标：运营能上传标准 CSV 并完成字段确认；Excel 直读作为后续增强。

交付物：

- 文件上传。
- CSV / Excel 解析。
- 标准模板下载。
- 字段映射确认。
- 导入校验。
- 异常行提示。
- 标准化记录生成。

验收标准：

- 上传一份问卷导出表后，系统能识别时间范围、项目、来源、地区、评分和原话。
- 字段识别失败时能手动修正。
- 存在隐私字段时能提示风险。

### M2：时间优先分析引擎

目标：建立日、周、月、季度、年、自定义时间段的统一分析能力。

交付物：

- 时间粒度模型。
- 时间范围选择。
- 项目集合选择。
- SQL 聚合接口或本地等价实现。
- 指标体系重算。
- 跨周期对比接口预留。

验收标准：

- 能查看单周、整月、季度、自定义时间段。
- 能在同一时间范围内选择全部项目、单项目、多项目。
- 指标和报告随时间 / 项目变化自动刷新。

### M3：自动 8 模块复盘报告

目标：上传并确认数据后，系统自动生成完整复盘。

交付物：

- 8 模块报告结构。
- 总报告生成。
- 专项报告生成。
- 证据原话引用。
- 报告复制 / 导出。

验收标准：

- 总报告能回答本期先处理哪里、为什么、证据是什么、下周动作是什么。
- 每个核心结论至少能展开 1 条证据原话。
- 专项报告不是总报告重复。

### M4：区域 / 服务中心深度下钻

目标：让区域运营和服务运营能定位到具体区域、城市和服务中心。

交付物：

- 全国 / 区域 / 城市 / 服务中心层级。
- 城市多选。
- 服务中心单点诊断。
- 原始评论分页 / 虚拟滚动。
- 好区域和风险区域典型清单。

验收标准：

- 能找出多个好区域典型和多个风险区域典型。
- 能展开服务中心原始评论，并按时间排序。
- 大样本不导致页面卡顿或信息失控。

### M5：Agent 追问层

目标：让运营可以围绕报告和数据继续追问。

交付物：

- 聊天入口。
- 问题相关性判断。
- 无关问题拒绝回答。
- SQL / BM25 / Vector 查询路由设计。
- 回答引用证据。
- 数据不足提示。

验收标准：

- 能回答当前数据相关的指标、地区、项目、时间、原话问题。
- 能拒绝无关问题。
- 回答不能脱离当前数据编造结论。

### M6：混合检索与数据库底座

目标：从前端 CSV 原型升级为可真实承载数据的 MVP 架构。

交付物：

- SQL 数据库 schema。
- 导入批次入库。
- 反馈记录入库。
- BM25 索引。
- Chunk / Vector 接口预留。
- 报告生成记录。
- Agent 查询日志。

验收标准：

- 结构化指标来自数据库。
- 精准原话检索可以通过 BM25 返回。
- 语义检索接口可以接入后续 Chunk / Vector 实现。

### M7：产品化交付增强

目标：让 MVP 更接近内部真实试点。

交付物：

- 报告历史。
- 报告版本。
- Markdown / Word 导出。
- 权限与角色预留。
- 大样本异步解析。
- 任务状态提示。

验收标准：

- 一周几百到几千条反馈可稳定分析。
- 月度或季度数据可以通过后台任务处理。
- 报告能进入周报、复盘会和服务中心跟进清单。

- 导入校验。

- 8 模块自动复盘。
- 指标体系。
- 证据原话追溯。
- 原始评论分页。

### P1 应该做

### P2 后续做

- 第三方问卷 API 对接。

- 细粒度权限。
- 多人协同。
- Chunk / Vector 深度语义检索完整实现。
- 更复杂的可视化看板。

## 14. 非目标

MVP 不做以下内容：

- 不自研完整问卷系统。
- 不替代问卷星、腾讯问卷、App 问卷。
- 不替代 CRM。
- 不替代工单系统。
- 不替代 NPS 系统。
- 不输出维修诊断或安全驾驶建议。
- 不把 Dashboard 作为主入口。
- 不把“提效比例”作为运营用户界面卖点。
- 不处理真实姓名、手机号、车牌、VIN、住址等敏感个人信息。

## 15. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 导入表格格式不统一 | 无法进入分析 | 做字段映射和标准模板，不依赖固定列名 |
| 报告像模板 | 用户觉得没有业务价值 | 每个结论绑定指标、原话和动作 |
| 指标体系不可信 | 运营不敢交付 | 每个指标提供口径说明和样本范围 |
| 大样本性能不足 | 真实场景不可用 | 分页、虚拟滚动、后台异步解析、指标缓存 |
| Agent 编造结论 | 降低信任 | 强制基于 SQL / BM25 / Vector 证据回答，证据不足时说明不足 |
| 时间和项目关系混乱 | 使用门槛高 | 时间作为第一层，项目作为时间范围内的集合对象 |
