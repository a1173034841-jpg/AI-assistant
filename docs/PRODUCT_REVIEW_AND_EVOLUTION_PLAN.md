# 产品缺陷检视与演进计划

> 检视日期：2026-06-04  
> 产品对象：主机厂售后反馈连续复盘与分析工作台  
> 当前结论：当前版本已经是可讲清楚价值的高保真前端原型，且测试与构建通过；但它还不是可交付给真实运营团队长期使用的 MVP。下一阶段不应继续扩功能面，而应把“真实导入 -> 字段确认 -> 自动复盘 -> 证据追溯 -> 报告导出 -> Agent 追问”的主路径打穿。

## 1. 当前产品判断

### 1.1 已经成立的部分

当前产品方向是成立的：它不替代问卷星、腾讯问卷、App 问卷、CRM、NPS 或工单系统，而是承接售后反馈导出表，把车主原话加工成运营可用的复盘材料。

现有代码和文档已经具备这些基础：

- React + Vite + TypeScript 前端工作台已经搭建完成。
- 标准 CSV 示例数据、本地 CSV 上传解析、字段别名识别已经接入。
- 导入校验已经覆盖业务项目、来源文件、时间范围、必填字段、指标覆盖和隐私风险。
- 工作台已经按“导入与自动复盘 -> 筛选与下钻 -> 报告与追问”三步组织。
- 已支持时间范围、项目集合、区域、城市、服务中心筛选。
- 已支持总报告、专项分报告、证据原话展开和复制报告。
- Agent 面板已经存在，并有本地规则回答与 DeepSeek 端口兜底。
- 2026-06-04 当前验证结果：`npm test` 通过 11 个测试文件、51 个测试用例；`npm run build` 通过。

### 1.2 尚未成立的部分

产品仍处在“可演示、可验证方向”的阶段，距离“运营真实可用”主要差在五件事：

1. 真实业务导入还不够稳：只有 CSV，缺少 Excel 直读、人工字段映射确认、异常行修复和多文件导入批次管理。
2. 报告交付还不够完整：现在只有复制，没有 Markdown / Word / 文本导出、历史报告和版本留存。
3. 大样本处理还不够真实：服务中心原始评论只展示最近 12 条，没有分页、搜索、排序、虚拟列表和后台异步处理。
4. Agent 还不是生产级：当前主要依赖前端状态、本地规则和浏览器直连 LLM，缺少后端代理、证据引用约束、会话持久化和检索底座。
5. 文档主线存在轻微分叉：PRD / MVP 文档偏“前端 MVP 补齐”，最终执行方案已经转向“上传自动复盘、时间优先、项目集合分析、Agent 追问、数据库与混合检索”。

## 2. 当前主要缺陷

### P0：阻碍真实 MVP 的缺陷

| 缺陷 | 当前表现 | 影响 | 建议 |
| --- | --- | --- | --- |
| 字段映射不可人工确认 | CSV 解析依赖内置表头别名，识别失败只能报错或跳过 | 真实问卷导出表字段不统一，运营无法自助修正 | 做字段映射确认页，支持自动识别、手动改列、保存本次映射 |
| Excel 直读缺失 | 当前文件选择只接受 `.csv,text/csv`，Excel 需另存 CSV | 主机厂运营更常拿到 Excel，导入门槛偏高 | 增加 `.xlsx/.xls` 解析，先支持第一个工作表和表头行选择 |
| 导入确认不完整 | 已有校验面板，但没有导入批次确认、项目名修正、异常行处理 | 上传后“系统判断是否正确”不可控，信任感不足 | 增加导入确认弹窗/页：项目、时间、记录数、异常行、字段映射 |
| 大样本原话不可用 | 服务中心下钻只展示最近 12 条评论 | 几千条反馈时无法搜索、翻页、定位证据 | 先做分页 + 搜索 + 低分/授权/场景筛选，再考虑虚拟滚动 |
| 报告不能导出 | 当前只有复制按钮 | 难进入周报、复盘材料和跨团队交付 | 增加 Markdown / TXT 导出；Word 可作为下一阶段 |
| Agent 生产链路不安全 | 浏览器端读取 `VITE_DEEPSEEK_API_KEY` 并直接请求模型 | API Key 暴露、CORS、审计和限流都不可控 | 生产版必须改为后端代理，前端只请求工作台 API |

### P1：影响产品可信度的缺陷

| 缺陷 | 当前表现 | 影响 | 建议 |
| --- | --- | --- | --- |
| 时间粒度还偏展示状态 | 有日/周/月/季度/年选项，但核心仍靠手动起止日期 | “时间优先”的产品目标没有完全落地 | 选择周/月/季度时自动计算默认日期范围，并支持前后周期对比 |
| 多文件导入批次不足 | 当前更像一次上传一个 CSV 并替换当前数据 | 同一项目多来源合并、跨项目批次复盘不顺 | 支持追加文件、移除来源、批次命名、来源列表 |
| 证据选择仍偏规则模板 | 报告来自规则归因和固定模板，LLM 只在 Agent 追问层尝试 | 报告容易被用户感知为模板化 | 把规则结果作为结构化骨架，再由 LLM 生成自然语言，但强制引用证据 |
| Agent 证据可见性不足 | Agent 回答记录显示证据数量，但没有把回答引用的原话直接展开 | 用户难判断 Agent 是否真的基于数据 | 每轮回答附“引用原话”折叠区，证据不足时明确说明 |
| 数据质量指标未形成决策门槛 | 有导入校验，但报告生成不一定受质量门槛影响 | 低质量数据也可能产出看似完整的报告 | 报告顶部展示数据可信度，异常/低覆盖时降级输出 |
| 隐私检测仍是轻量规则 | 通过正则检测手机号、VIN、车牌、地址 | 只能挡明显风险，不能覆盖企业合规要求 | 明确 MVP 只处理脱敏测试数据；生产版加后端脱敏和审计 |

### P2：影响后续规模化的缺陷

| 缺陷 | 当前表现 | 影响 | 建议 |
| --- | --- | --- | --- |
| 无数据库与历史报告 | 当前数据主要存在前端状态里 | 无法沉淀批次、报告、追问和复盘版本 | 建立轻量后端和数据库，再做历史报告库 |
| 无 BM25 / 向量检索 | 原话证据主要来自规则筛选和数组处理 | Agent 深度追问和复杂语义召回受限 | 先上 SQL + FTS/BM25，向量检索后置 |
| 无异步任务 | 前端同步解析和计算 | 月度数万条反馈时性能和体验会下降 | 后端解析、指标缓存、报告生成任务化 |
| 无角色权限 | MVP 明确暂不做登录权限 | 试点阶段外发给团队使用会受限 | 试点前补最小角色：运营查看、报告编辑、管理员 |
| 文档口径不完全统一 | 旧文档仍有项目优先、手动工作流口径 | 后续开发容易目标漂移 | 统一以最终执行方案为主线，更新 PRD / MVP / DEV_DESIGN |

## 3. 演进原则

### 3.1 先闭环，不扩边界

下一阶段不要优先做可视化 Dashboard、第三方问卷 API、CRM 回写、复杂权限或多人协作。最重要的是让一个运营用户可以上传真实问卷表，确认字段后，得到可交付报告，并能追溯证据。

### 3.2 时间优先，项目是时间范围内的分析对象

售后运营不是一次性项目分析，而是连续复盘。产品主层级应是时间：日、周、月、季度、年、自定义；项目、区域、城市、服务中心都是时间范围内的下钻维度。

### 3.3 报告必须绑定证据和动作

每个结论至少要绑定一个指标或一条原话。报告不是“总结一下”，而是回答：发生了什么、证据是什么、谁要处理、怎么处理、下次看什么。

### 3.4 Agent 必须受数据约束

Agent 不是开放聊天助手。它只能回答当前数据、指标、报告结论、原话证据和售后运营动作相关问题。证据不足时要拒绝或降级回答。

## 4. 分阶段演进计划

### M0：产品主线冻结与文档对齐

目标：统一后续开发口径，避免在“报告工作台”“文本效率工作台”“数据分析与 Agent 工作台”之间摇摆。

范围：

- 确认主定位：售后反馈连续复盘与分析工作台。
- 确认 MVP 第一目标用户：区域运营、服务运营、用户运营。
- 将 PRD、MVP_SCOPE、DEV_DESIGN、DATA_AND_ANALYSIS_SPEC 对齐到“上传自动复盘、时间优先、项目集合分析、Agent 追问”。
- 明确品牌口碑团队是扩展用户，不再驱动 MVP 架构。

验收门槛：

- 文档中不再出现互相冲突的主流程。
- 后续任务均能映射到一条主链路：导入 -> 校验 -> 复盘 -> 下钻 -> 交付 -> 追问。

### M1：真实导入闭环

目标：运营能上传真实问卷导出表，并完成字段确认。

范围：

- CSV 多文件追加导入。
- Excel 直读，至少支持 `.xlsx` 第一个工作表。
- 字段映射确认 UI。
- 导入批次确认：项目名、时间范围、来源数、记录数、异常行。
- 异常行列表：缺字段、时间无法识别、评分非法、隐私风险。
- 导入后可修改映射并重新标准化。

验收门槛：

- 上传一份非标准表头 CSV 或 Excel 后，运营可以手动映射并生成报告。
- 异常行不会静默丢失，用户能看到原因。
- 同一时间范围内可以合并多个来源文件。

### M2：可信报告与交付

目标：报告从“看起来像模板”升级为“可进入周报和复盘会”。

范围：

- 总报告和 5 类专项输出继续保留，但每段都要绑定指标或证据原话。
- 增加 Markdown / TXT 导出。
- 增加服务问题闭环清单导出。
- 报告顶部展示数据可信度：样本量、字段完整率、指标可计算率、隐私风险。
- 证据原话支持按低分、授权联系、服务场景、服务中心筛选。
- 原始评论分页、搜索、排序。

验收门槛：

- 一份真实或仿真的 500-1000 条反馈数据可以生成可复制、可导出的报告。
- 用户可以从报告结论下钻到原话、评分、时间、城市、服务中心和来源。

### M3：Agent 正式化

目标：Agent 从演示追问升级为可信的数据分析入口。

范围：

- 前端不再直连模型，改为后端代理。
- 建立问题分类：数据盘点、指标解释、风险定位、证据查找、回访清单、报告改写、无关拒答。
- 每轮回答必须绑定当前筛选范围。
- 每轮回答展示引用原话。
- Agent 会话按项目集合和时间范围保存。
- 证据不足时给出“当前数据不足以判断”的回答，而不是硬生成结论。

验收门槛：

- Agent 能回答当前项目/时间/城市/服务中心相关追问。
- Agent 对无关问题稳定拒答。
- Agent 回答可以展开证据原话。

### M4：数据底座与检索

目标：支撑真实业务规模、历史报告和复杂追问。

范围：

- 建立后端 API。
- 建立数据库表：导入批次、来源文件、反馈记录、报告运行、报告段落、证据原话、Agent 消息。
- 结构化指标走 SQL。
- 精准原话查找走 BM25 或全文检索。
- 向量检索先预留接口，不作为第一批必做。
- 月度大样本解析改为异步任务。
- 报告生成结果缓存。

验收门槛：

- 千级样本前端不卡顿。
- 万级样本可以异步解析并返回报告任务状态。
- 历史批次和历史报告可查询。

### M5：试点商品化

目标：让产品具备小范围真实试点能力。

范围：

- 试点角色：区域运营、服务运营、用户运营。
- 最小登录与角色权限。
- 报告历史、版本和重新生成。
- 试点反馈收集：报告是否可用、节省时间、缺少哪些字段、哪些结论不可信。
- 建立演示数据、压测数据和真实试点数据三套数据集。

验收门槛：

- 3 类售后运营角色都能完成各自任务。
- 单次复盘从“人工整理数小时”下降到“导入确认后 10-20 分钟内可交付初稿”。
- 至少 3 份试点报告被真实复盘场景使用。

## 5. 近期建议任务清单

### 第一优先级：1-2 天

- 统一 PRD / DEV_DESIGN / MVP_SCOPE / DATA_AND_ANALYSIS_SPEC 的主流程表述。
- 把“字段映射确认”和“导入确认”设计成独立页面状态。
- 明确生产版 Agent 不允许浏览器直连 API Key。

### 第二优先级：3-5 天

- 做字段映射确认 UI。
- 支持 Excel 直读。
- 支持多文件导入和来源列表。
- 做异常行列表和重新映射。

### 第三优先级：1 周

- 做原始评论分页、搜索、低分/授权/场景筛选。
- 做 Markdown / TXT 报告导出。
- 把 Agent 回答的证据原话直接展示出来。

### 第四优先级：2-3 周

- 建轻量后端和数据库。
- 做导入批次、报告历史和 Agent 会话持久化。
- 引入全文检索/BM25，支撑证据查找和 Agent 追问。

## 6. 不建议近期投入的事项

- 不优先做完整问卷创建器。
- 不优先接问卷星、腾讯问卷 API。
- 不优先做复杂 Dashboard。
- 不优先做企业微信、CRM、工单系统回写。
- 不优先做完整多人审批流。
- 不优先做深度向量检索，除非 BM25 和规则证据选择已经无法满足试点问题。

## 7. MVP 通过标准

真正 MVP 的通过标准不是“页面有多少模块”，而是以下闭环是否成立：

1. 运营上传一份真实问卷导出 CSV 或 Excel。
2. 系统识别字段，运营可手动确认或修正。
3. 系统展示导入质量：记录数、时间范围、字段完整率、异常行、隐私风险。
4. 系统按默认时间范围自动生成 8 模块复盘。
5. 运营可以按项目集合、区域、城市、服务中心下钻。
6. 每个核心结论可以展开原话、评分、时间、城市、服务中心和来源。
7. 报告可以复制和导出。
8. Agent 能围绕当前数据继续追问，并能展示证据。
9. 大样本不会因为一次性渲染原话而卡顿。
10. 至少区域运营、服务运营、用户运营三类角色都能在同一主流程里完成任务。

## 8. 总结

当前产品最大的优点是方向已经收敛：它不是问卷工具，也不是泛泛的 AI 总结器，而是售后运营把车主原话变成交付材料的效率工作台。

当前产品最大的风险也很清楚：如果导入、字段确认、证据追溯、报告导出和 Agent 可信度不闭环，它会停留在“好看的演示原型”。下一阶段应先补真实 MVP 的硬门槛，再谈数据库、权限、历史报告和更复杂的语义检索。

最推荐的演进顺序是：

```txt
文档主线统一
-> 字段映射与真实导入
-> 原话分页与报告导出
-> Agent 证据化
-> 后端数据库与检索
-> 试点商品化
```
